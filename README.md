## 🧠 Socratic Problem-Solving Checklist

For every new problem, complete these steps before looking at a solution:

- [ ] Restate the problem in my own words.
- [ ] Write down the input, output and constraints.
- [ ] Work through one normal example by hand.
- [ ] Identify edge cases.
- [ ] Explain a straightforward approach in plain language.
- [ ] Look for a better approach and explain why it works.
- [ ] Implement in Python.
- [ ] Implement in C++.
- [ ] Test normal cases and edge cases.
- [ ] State time and space complexity in my own words.
- [ ] Record one mistake or insight.

### ✅ When does a problem count?

A problem counts toward the 150 only when I can independently explain the approach, produce a correct implementation, test important edge cases, and discuss complexity. A copied solution or a solution I cannot explain does not count.

## 🧪 Python and C++ Code Quality Checklist

<details>
<summary><strong>Python review checklist</strong></summary>

- [ ] Use descriptive `snake_case` names.
- [ ] Keep functions focused and small.
- [ ] Avoid unnecessary global state and repeated work.
- [ ] Understand list mutation, copying and slicing before using them.
- [ ] Check empty inputs, one-element inputs and boundary values.
- [ ] Explain the time and auxiliary-space cost.

</details>

<details>
<summary><strong>C++ review checklist</strong></summary>

- [ ] Use clear types (`int`, `long long`, `double`, `std::string`, `std::vector`).
- [ ] Prefer `const` references for read-only large objects when appropriate.
- [ ] Understand when a value is copied and when an object is modified.
- [ ] Use standard containers and algorithms appropriately.
- [ ] Avoid out-of-bounds access and unintended allocations.
- [ ] Check integer overflow and signed/unsigned conversions.
- [ ] Use pointers only when the concept is part of the lesson and ownership is clear.

</details>

## 🏁 Personal Operating Rules

1. **Understand before optimizing.** Write down the simple approach first.
2. **No solution copying.** Hints are allowed; unexplained code does not count as progress.
3. **Use both languages.** Python builds speed; C++ builds discipline around types, memory and performance.
4. **Test edge cases.** Empty, single-element, duplicate, boundary and large inputs matter.
5. **Review mistakes.** Re-solving an old problem is part of learning, not going backward.
6. **Protect consistency.** Four focused hours is the plan; record actual time honestly and adjust when needed.
7. **Connect to systems.** Ask how the pattern appears in memory management, caches, queues or inference serving.
